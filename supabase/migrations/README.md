# กติกาของโฟลเดอร์ migrations

## ลำดับการรัน

ไฟล์รันเรียงตามชื่อไฟล์ (เลขนำหน้า 4 หลัก) โปรเจกต์นี้ไม่ได้ใช้ Supabase CLI
เลขพวกนี้จึงเป็นข้อตกลงของคนอ่านล้วน ๆ ไม่ใช่สิ่งที่เครื่องมือบังคับ
ตัวที่บันทึกลำดับจริงคือตาราง `supabase_migrations.schema_migrations` บนเซิร์ฟเวอร์
ซึ่งใช้ timestamp ของตอนที่ apply ไม่ใช่เลขนำหน้าไฟล์

## เลข 0035 ซ้ำกันสองไฟล์ — ตั้งใจปล่อยไว้

```
0035_multi_slot_bookings.sql
0035_refund_bank_details.sql
```

ทั้งคู่ apply ไปแล้วตามลำดับนี้บน production และพอเรียงตามชื่อไฟล์ก็ได้ลำดับ
เดียวกันพอดี (`multi` มาก่อน `refund` ตามตัวอักษร) จึงไม่มีผลเสียในทางปฏิบัติ

**ไม่ไล่เลขใหม่ให้ตรง** เพราะเลข migration ถูกอ้างอิงในคอมเมนต์ทั่วโค้ดหน้าเว็บ
ประมาณ 130 จุด (เช่น `// ดู 0054`, `// (0094) การลบข้อความ`) การเลื่อน
0036–0098 ขึ้นหนึ่งตำแหน่งจะทำให้คอมเมนต์เกือบร้อยจุดชี้ผิดไฟล์ทันที
ซึ่งแย่กว่าเลขซ้ำสองไฟล์ที่เรียงถูกอยู่แล้วมาก

ไฟล์ใหม่ให้ใช้เลขถัดจากตัวที่สูงสุดในโฟลเดอร์ และอย่าใช้เลขซ้ำอีก

## ห้าม apply โดยไม่เขียนไฟล์

เคยเกิดขึ้นมาแล้ว — มี migration 5 ตัวถูก apply ผ่าน MCP/SQL Editor โดยไม่เคย
ถูกเขียนกลับมาเป็นไฟล์ในโฟลเดอร์นี้:

| migration | ผลถ้าหายไป |
|---|---|
| `restrict_booking_rpcs_from_anon` | `anon` ยิง `create_booking` ได้อีกครั้ง |
| `support_tickets_revoke_anon_execute` | `anon` ยิง RPC ชุดติดต่อเราได้ 5 ตัว |
| `chat_messages_replica_identity_full` | ลบข้อความแชทแล้วอีกฝ่ายไม่เห็นว่าถูกลบ |
| `chat_mark_unread_precision` | กด "ทำเป็นยังไม่อ่าน" แล้วได้ข้อความเกินหนึ่งใบ |
| `seed_sport_descriptions` | คำอธิบายกีฬาเป็น placeholder |

ทั้งหมดถูกกู้กลับมาแล้วใน `0100_restore_untracked_production_migrations.sql`

**ทุกครั้งที่ apply ต้องเขียนไฟล์คู่กันเสมอ** ไม่งั้นวันที่ต้องสร้างฐานใหม่
(db reset / branch / ย้ายโปรเจกต์) จะได้ฐานที่ไม่เหมือน production
โดยไม่มีอะไรฟ้องเลย

วิธีเช็คว่าตรงกันหรือยัง:

```sql
-- เอาผลไปเทียบกับรายชื่อไฟล์ในโฟลเดอร์นี้
select version, name from supabase_migrations.schema_migrations order by version;
```
